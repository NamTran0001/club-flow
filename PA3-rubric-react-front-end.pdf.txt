Due Monday, November 30, 2026, 22:00. This is the third milestone of your project: your
team builds the whole main ﬂow of ClubFlow as a React app, from publishing a campaign to
the applicant seeing the result, for all three roles. The app gets every piece of data from an API,
and that API is written down ﬁrst: your team writes the endpoint contract in docs/api/ ,
builds a small mock server that answers exactly as the contract says, and only then has the

without the front end changing. The ﬂow and the list of problems to avoid are in the ClubFlow
ﬁnal project brief. This rubric is the brief for PA#3.
Use your assistant. Nothing in this milestone asks you to type code yourself: it scores what the
app does in a browser, what the contract says, what you told the assistant, and how you
checked what it wrote.

The contract — docs/api/
Write it before the assistant writes the code that calls it, and give it to the assistant as the
thing to follow.
docs/api/README.md  — the base path (/api ), how a request says who is calling
(Authorization: Bearer <token> ), one error shape for the whole API, the status codes you
use, and a table of every endpoint: method, path, the roles that may call it, the ﬁle that
describes it.
One ﬁle per resource (docs/api/campaigns.md , docs/api/applications.md …). For each
endpoint: who may call it; the path and query parameters; the body, with each ﬁeld's type,
whether it is required and its limits; the success answer; and every error answer that can
happen — 400  with a message per ﬁeld, 401 , 403 , 404 , 409  where they apply.
Examples we can send. Each endpoint has at least one example: a request block followed
by the answer block, both fenced as http :
`text http POST /api/auth/login Content-Type: application/json
{"email": "studenta@clubﬂow.test", "password": "studenta-demo"} ```
```http HTTP/1.1 200 OK Content-Type: application/json
{"token": "…", "user": {"id": "u-studenta", "name": "Student A", "role": "applicant"}}
Where a request needs a token, write Authorization: Bearer {{token:studentA}} , with a name
from the Demo accounts table of FRONTEND.md ; we sign in as that account and put its token
there. …  stands for anything: a value ("token": "…" ), an object ({…} ), a list ([…] ), or more
items or ﬁelds at the end (, … ). An upload may be written as a curl  line in a sh  block instead.
We send docs/api/README.md  ﬁrst, then the other ﬁles of docs/api/  in alphabetical order, each
from top to bottom, to one freshly started mock: write the examples so that they work in that
order (number the ﬁles, 01-auth.md , if your ﬂow needs another order). - A ## Changes  section

at the end of each ﬁle. Once front-end code calls an endpoint, every later change to it gets a
line here: the date, what changed, and why.
The mock — mock/server.mjs
node mock/server.mjs  starts it on the port in PORT , 3001 by default. It uses only Node's
built-in modules (node:http , node:fs …), so it runs with no npm install  — that is how we
run it.
It starts from the data in mock/data/ , keeps every change in memory, and starts over when
restarted. The data tells the brief's example story.
MOCK_MODE  sets how it answers: normal  (after about 150 ms), slow  (after 2 s), error  (500
with your error shape, for every request except sign-in), empty  (every list in an answer is
[] , including a list inside an object; a single object — one campaign, one application — still
answers).
It accepts the demo accounts at sign-in and answers with a token and the user's role; the
other requests read that token to know who is asking. A made-up token is ﬁne here, but it
must still work after the mock restarts (for example token-<user id> ): we restart the mock
to change modes, then press Retry.
It answers every example in docs/api/  exactly as written, and it can show every state the
steps need — a campaign that fails to publish, a duplicate application, a draft with
Proposed, Unassigned and Conﬂict rows, a refused conﬁrmation, a conﬁrmed schedule. It
does not have to compute the schedule: ﬁxed answers from mock/data/  are ﬁne. An
uploaded CV may be ignored.
It prints one line per request: method, path, status.
The front end calls only relative paths (/api/applications , never
http://localhost:3001/… ). In client/vite.config.js , forward /api  to http://localhost:3001  in
both server.proxy  and preview.proxy , so npm run dev  and npx vite preview  both reach the
mock. In PA#4 your Express server listens on the same port.
